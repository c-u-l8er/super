# ampd — the [&] Super authority runtime (C1)

The first real subsystem: the capability system as supervised OTP
processes plus a gateway module, semantically conformant to the frozen
browser simulator.

    Ampd.Supervisor (one_for_one)
    ├─ AuthorityCoordinator  the total order over authority change + effect claims
    ├─ Session               ambient context: workspace · current run · retired runs
    ├─ CapabilityRegistry    what exists: packs, versions, surfaces, policies
    ├─ GrantRegistry         what may be exercised: grant objects + draft + snapshot
    ├─ Approvals             which exact effects await consent (intent digests)
    ├─ Receipts              the effect ledger — durable (DETS, survives crash & restart)
    └─ Effects               the effect journal — effect-request@1 / effect-attempt@1
       Ampd.Gateway          the one door (module) — seal → grant → placement → approval → claim → receipt
       Ampd.Control          the command surface: general channel vs human control
       Ampd.Authority        the linearized public API; typed commands enter here
       Ampd.Ordered          makes the coordinator boundary mechanical, not documentary
       Ampd.Refusal          refusal@1 — one refusal, two projections
       Ampd.Core             pure parity layer: canon/sha256/digests/refusal strings
       Ampd.World            world-meta@1 — world identity, recovery truth table, lineage
       Ampd.Bootstrap        the explicit initialization transition (zero authority)
       Ampd.Store            truth-preserving recovery; seals rather than reseeds

## Crash truth (C1.0a)

Every registry persists through `Ampd.Store` (DETS) and recovers its own
truth: restart never widens authority. The crash falsifiers kill
GrantRegistry after a revoke, Session after ending a run, Receipts after
a commit, and Approvals while consent is pending, then assert revoked
stays revoked, retired stays retired, and receipts and pending consent
both survive. Test data lives under /tmp; runtime data under `priv/data/`.

## Bootstrap truth (C1.0b)

**Installation confers zero authority — and so does boot.** A production
world is created by `Ampd.Bootstrap.new_world!/0` and holds nothing:
`Ampd.reset/0` gives you that world, `Ampd.reset_demo/0` gives you the C0
conformance fixture, and only the second one mints a grant.

**Bootstrap may create authority state only through an explicit
initialization transition. Recovery may never infer authority from
defaults.** `world-meta@1` is written *after* every store is seeded, so a
manifest on disk proves the stores were real. Four states, and only one
may create authority:

    manifest absent  + no authority store    → FIRST BOOT  (may initialize)
    manifest present + every store present   → EXISTING    (load truth)
    manifest present + store missing/damaged → SEALED      (refuse, named)
    manifest absent  + any store present     → ORPHANED    (refuse, named)

The fourth looks exactly like the first. A world whose manifest was lost
still has its authority on disk, and seeding over it would destroy the
evidence *and* replace it with defaults — the same widening the manifest
exists to prevent, arriving from the other direction.

A sealed registry serves no authority, refuses to be written, projects a
neutral empty state rather than `initial/0` defaults, and the gateway
turns the seal into a named refusal rather than a crash loop — an outage
tells you nothing, and every refusal here names what to fix. DETS is
opened with `repair: false` for the same reason: a silently repaired
authority table is an unaudited mutation, so damage seals as
`RECOVERY-STATE-UNTRUSTED`.

**Generation is world lineage, not a write counter.** It advances only
when durable truth is wholesale replaced — restore, factory
re-initialization, import. A semantics-preserving migration moves
`schema_version` instead. Restoring a generation-3 snapshot into a
generation-7 world produces **generation 8** carrying `restored_from`, so
a stale client can never read a rollback as continuity.

## Authority linearization (C1.0b.1)

**CLAIM is the authority boundary.** Every authority-changing command and
every effect claim passes through `Ampd.AuthorityCoordinator`, giving them
one total order:

                       AuthorityCoordinator
                               │
             ┌─────────────────┼─────────────────┐
        request_grant     revoke_grant      claim_effect
             └─────────────────┴─────────────────┘
                               │
                         TOTAL ORDER

Before the claim, revocation wins — `perform` re-decides *inside* the
order, so a verdict sampled earlier cannot ride into a claim taken after
the revoke returned. After the claim, the effect holds a lease for its
frozen snapshot; a later revocation does not retroactively cancel an
effect that may already have touched the world. The adapter runs
**outside** the lock on purpose: holding authority across a remote call
would make every revocation wait on someone else's TCP timeout.

`Ampd.Authority` is the public API. The registry functions are primitives
the coordinator calls once it holds the order — calling
`GrantRegistry.revoke_domain/1` directly is unordered against a concurrent
claim, which is the defect this removes. C1.1's typed projection commands
enter through `Ampd.Authority`.

### Three entry points, deliberately distinct

    preflight/4       advisory      creates nothing, stales nothing
    request_effect    ordered       may open a proposal + pending approval
    perform/5         ordered       re-checks, claims, acts

`decide/4` is internal. It was never read-only — for approval-class
capabilities it opened pending approvals and staled prior consent, so a
bare call mutated approval state *outside* the total order. It now refuses
callers outside the coordinator.

The coordinator boundary is enforced, not documented: a GenServer receives
its caller, so an authority-bearing mutation is served only when that
caller is `AuthorityCoordinator`. Anything else gets
`unordered-authority-mutation` and nothing moves. `CapabilityRegistry`'s
install/update are `handle_call` for exactly this reason — **a cast
carries no caller, so a mutation that cannot be attributed cannot be
ordered.**

A sealed registry refuses by name rather than raising: the mutation now
arrives from the coordinator, and a raise would take the total order down
with it, turning one lost store into a node-wide outage.

### Two channels (C1.1.0)

    GENERAL CHANNEL          HUMAN CONTROL CHANNEL
    ────────────────         ─────────────────────
    projection               approve_effect
    preflight (advisory)     deny_effect
    request_effect           revoke_grant
    request_grant            recover_world
    inspect_refusal

Every local process runs as the same OS user, so "same UID" proves
nothing. An agent may **ask** for anything and may never **give** consent.
`refusal@1` carries `code · retryable · requires_human · public_message`
for the general channel and `operator_detail` only for human control — the
agent learns what to do without reading which store is gone.

**The transport is C1.1 proper.** Until the private inherited channel from
the Tauri host exists, `origin` is supplied by the caller and is *not yet*
a trust boundary — it is where the trust boundary goes.

`Ampd.Control.approve_effect(request_id, approval_id)` is the product API;
`Gateway.approve_last/0` survives only as a conformance helper, because
"approve whatever is last" is the wrong identity semantics once two
effects are in flight.

### Effect identity ≠ consent identity

    effect-intent@1   → effect_key       what should happen
    approval-intent@1 → approval_digest  why this actor may do it now
                        (embeds effect_key + actor + grant
                         + authority snapshot + placement + pack version)

The **idempotency key is `effect_key`**, never the approval digest. If it
carried the authority snapshot, reconciling an UNKNOWN effect after an
unrelated grant change would hand the far side a different key for the
same desired effect — deduplicating against nothing. `effect-intent@1`
carries no actor, grant, snapshot, or placement, and a falsifier asserts
it never gains one.

## Effect atomicity (C1.0b)

    PROPOSED → AUTHORIZED → APPROVED → CLAIMED → ATTEMPTED
                                                  ├→ COMMITTED
                                                  ├→ FAILED
                                                  └→ UNKNOWN → RECONCILE

`Ampd.Gateway.perform/5` writes the journal before it touches anything:
CLAIMED is durable *before* consent is consumed, ATTEMPTED is durable
*before* an adapter would be called. The claim is a single serialized
call, so two racing exercises cannot both hold one proposal. Anything
still in flight at restart recovers as UNKNOWN and is queued — never
resolved by guessing — and an UNKNOWN effect cannot be re-claimed,
because its adapter may already have changed the world. The idempotency
key is the intent digest Super already computes, which is what makes an
UNKNOWN outcome replayable against a far side that deduplicates.

`Ampd.Gateway.authorize/4` keeps the C1.0a contract (decide *and*
consume) so the vectors stay meaningful; `decide/4` consumes nothing.

## Deliberately not in C1.0b

No adapters, no secrets store, no network effects, no UI socket. The
adapter slot in `perform/5` takes a function and the default does
nothing — that is the only simulated part of the effect path. DETS is
durable to disk, not replicated, and its 2 GB ceiling and per-table
recovery are the two facts that will force the move to SQLite before
real connectors ship. C1.1 is the projection protocol: the frozen
prototype UI switches from SIMULATED to live-local by subscribing to
these processes over typed commands, never raw registry mutations.
